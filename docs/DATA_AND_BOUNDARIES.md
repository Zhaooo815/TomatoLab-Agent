# Data and boundaries

## 数据从哪来

- 事实源：课程提供的 protocol（`.docx`，八个部分、6518 字符），原文 PDF 放在 `frontend/public/protocol/`，由原文档直接导出、未改字。
- 结构化：`frontend/src/data/tomato.ts`（七环节 `STAGES`、参数卡 `PARAMS`、培养基 `MEDIA`、母液 `STOCKS`、待核对 `CHECKS`、问答库 `QA`、安全块 `SAFETY`）；长篇整理见 `docs/COURSE_PROFILE.md`。
- 协议差异清单：`docs/PROTOCOL_OPEN_QUESTIONS.md`，与代码里的 `CHECKS` 一一对应。
- 界面上所有数值都能回到协议小节，代码里每条数据都带 `source` 字段。

## 三条边界

1. **不代写完整实验报告**。工具给框架、给每段该写什么、给常见扣分点；被要求「写一份完整报告」时降级为框架建议。
2. **不造原始数据**。不提供可填的假数据表，也不把没做的实验写成做成了。被要求「把结果调好看一点」时，改为如实记录异常、做误差归因。
3. **有出处才下结论**。回答带〔协议·小节〕标注；查不到就写查不到；协议内部冲突只提示差异，不改数。

## 已知局限

- 检索是关键词匹配，同义词覆盖不全，问法太绕时可能落空——这是设计如此，宁可说「没有」也不硬答。
- 单机版台账存在浏览器 localStorage，换设备会丢；多人同步只在线上版具备。
- 报告自查是按关键词判要素，属于结构性提示，不等于内容正确。
- 教师端不在本仓库，多人并发与覆盖问题未在本地复现。
